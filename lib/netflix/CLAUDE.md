# `lib/netflix/` — browse-gallery ripping, IMDb ratings, the player remote

The measured detail behind `gigaku titles` and the mouse buttons' half of the Netflix
player. The map is the repo-root `CLAUDE.md`.

- `gallery.py` — the rip. Drives the page's **own falcor client**, a MAIN-world global: `netflix.appContext.state.pathEvaluator.get(['genres', <id>, 'su', {from,to}, FIELDS])`. Do **not** rebuild the `/api/shakti/…/pathEvaluator` request by hand — the client already holds the endpoint, build id, auth token and ESN, and surviving a Netflix build bump means asking *it*, not re-deriving them. Measured facts the code depends on: **(1)** the endpoint runs a **path whitelist** — only `itemSummary`/`availability`/`episodeCount`/`summary`/`queue`/`inRemindMeList` resolve for a slot, the rich per-video leaves (`synopsis`, `genres`, `cast`, `runtime`, `tags`) are refused on `videos/<id>`, and **one** unknown leaf fails the *whole* request with a bare `xhr error`, so `FIELDS` is a closed set (genres/runtime come from IMDb instead); **(2)** titles come back in **English** even on a `/de` gallery, which is what makes the IMDb join tractable; **(3)** past the end, slots materialise **present-but-empty** rather than erroring — that's the stop condition, so the rip never needs a total (there is no `su/length`: it's refused too); **(4)** the endpoint **rate-limits bursts** — parallel windows fail with `xhr error` and the same window succeeds seconds later, so windows go one at a time with a delay and a failed window is retried up to 3× before it's believed. `fetch` is async and one AppleScript call can't both start and await it, so every window is **kick → poll → chunked read → free**, tagged per window so a stale buffer can't be read as this window's answer; the read is length-checked because a silently truncated AppleScript string would parse as a short-but-valid gallery. Progress is saved atomically after every window, so Ctrl-C resumes. `probe()` is the diagnostic for when a build change breaks it.
- `imdb.py` — the ratings join, from IMDb's **own datasets** (`datasets.imdbws.com`: official, complete, daily, no key, no rate limit). `title.basics` is ~225 MB / 11.7 M rows, so it is streamed once and **reduced** — dropping the ~9.8 M `tvEpisode` rows (a gallery slot is never a single episode) — and the raw download deleted; steady state is ~65 MB of slims. Matching is a transparent ladder, not a fuzzy-match dependency: normalised title keys (`norm()` folds case/accents/`ß`/`&`/punctuation) at descending weights (whole title, before a colon, minus a `Season N` tail, minus a leading article, minus a Netflix-only parenthetical like `The Office (U.S.)`), then year, then medium. Two things the real data forced: a **show's** Netflix `releaseYear` is its *newest* season (`The Handmaid's Tale` reads 2025 against IMDb's 2017), so year-inside-the-run counts as a hit; a **film's** year is reliable, so a gap over 5 years is penalised steeply enough to *reject* — otherwise a same-named different film attaches as a weak match (`Rich in Love` 2020 → a 1992 film). Whatever the local scan rejects goes to IMDb's unauthenticated **suggestion endpoint** (paced, capped, cached on disk), which resolves alternate titles server-side. Every row records `match_source`/`match_confidence`/`match_score`/`match_note`, and `"none"` means *nothing was attached* — never a chosen candidate (a row reading `source: suggestion, confidence: none` claimed both at once, and that was a bug). Ranking is a **shrunk mean** (`IMDB_BAYES`), so 9.5-from-40-votes can't outrank 8.5-from-200k. These caches are **deliberately not** in `backup.MANAGED`: unlike `words.json` they all re-download.
- `watched.py` — what you've already seen, from the **Netflix Watched Marker** extension (`dbnjnblicgfgambjhbffkgihmlfokefn`). It keeps a flat array of Netflix ids in `chrome.storage.local` under `myNFWatchedList`, and that is **not** reachable from here: AppleScript's `execute javascript` runs in an *isolated* world even on an extension page, where `chrome` exists but `chrome.storage` is **undefined** (measured — don't retry this). Reading its LevelDB would mean a new dependency and a private format. So we use the extension's **own supported export**: open its popup, click `#btnBackupWatchedList`, and read the `~/Downloads/Netflix Watched List (<when>).txt` it writes (one id per line), then delete it. A synthetic click from the isolated world still fires the popup's own jQuery handler because both share the DOM — the same trick `subs.py` uses on Language Reactor's export button. Ids are cached in `TITLES_DIR/watched.json`, and the whole thing is **best-effort**: no extension, or a Chrome set to "Ask where to save each file", degrades to the cache instead of failing the command (`--no-watched` skips it). Nothing here ever writes to the extension.
- `markers.py` — the **Anime** / **Korean** labels, from Netflix's own **per-title genre rows** (`videos/<id>/genres`, batched `TITLES_GENRE_BATCH` ids per call). Those rows carry the original language beside the taste labels — Dark → `German`, All of Us Are Dead → `Korean · K-Dramas based on Webtoon`, Sword Art Online → `Anime Series · Japanese`, One Piece → `TV Shows Based on Manga`, Rick and Morty → `Sitcoms` — so a keyword rule over them is Netflix's answer, not an inference. Nothing else can answer it: `itemSummary` has no language or country, IMDb's `title.basics` has no country/language column (`title.akas` is half a gigabyte and answers a different question), and an IMDb genre guess is actively wrong — IMDb calls Rick and Morty "Animation". Names are kept per record as `nf_genres` (richer than IMDb's), so a rule change costs no refetch; results cache to `TITLES_DIR/nf-genres.json` and only unseen ids are fetched. **Two dead ends not worth re-walking, both recorded in the module:** genre *galleries* are storefronts, not the catalogue (7424 "Anime" = 307 titles, and eight anime sub-genres of 19–218 each still missed One Piece); and `videos/<id>/genres` **is** whitelisted — a first pass that probed 25 fields in one burst had them refused by the rate limiter, which is indistinguishable from "not allowed". Hence `gallery.retrying()`: never trust a single `xhr error`, and never batch-probe fields. Best-effort throughout; `--no-mark` skips it.
- `store.py` — the record shape (`FLAT_COLUMNS` *is* the CSV header and the page's keys, one definition), the flat projection, atomic JSON, CSV/TSV. Keeps Netflix's `itemSummary` under `raw` verbatim, so a field nobody projected is still there next month without a re-rip.
- `titles.py` + `titles_page.html` — orchestration and the page, mirroring `plots.py`'s `build`/`render(data, out)`/`main` and the `__DATA__` sentinel. One command, not three: the expensive stages (rip, dataset download) skip themselves on a fresh cache, so re-ranking is a sub-second re-render. The page is a sortable/filterable table with an **Unmatched** tab — a bad or missing match must be *visible*, never quietly dropped. Two things live only in the browser: **Hide watched** is the default filter (the question is what to watch *next*), and the **Gigaku List** is a hand-made shortlist whose toggle replaces the rank column — stored in `localStorage` keyed by `genre_id`, because a `file://` page cannot write to disk and localStorage is keyed by origin, so it survives `gigaku titles` regenerating the file. Watched titles already on that list are pruned by an explicit button, never silently: the list is hand-made, so emptying part of it is a decision rather than a side effect. `TITLES_HIDE_GENRES` (default `Crime,Documentary`) drops whole genres — any title carrying one, so "Crime" takes the crime-dramas too — and it is applied in `build()`, **not** in the rip: the dump and the CSV keep every title, so changing your mind costs a re-render rather than a re-rip. Column order is Title then **Genres**, before type/year/ratings. **No `<img>`**, deliberately: every record carries an `https` boxart URL and 4,000 of them would turn a self-contained page into an online-only one (a test asserts this).
- `remote.py` + `chrome/gigaku/remote-keys.js` — the **mouse buttons' half of the Netflix player** (`scroll_volume.py`): left = play/pause, right = fullscreen. `remote.py` only *posts a key*; the behaviour lives in the extension, and the split is forced rather than chosen — **fullscreen can only be entered from inside a real user gesture**, so the two halves are "make a gesture" and "be inside it", and no one process covers both. Everything below was measured against a live `/watch` tab, 2026-08-04, and every one of these was first believed on a single lucky reading and then disproved by a second: **(1)** a virtual keycode is a *position* and the character comes from the **active input source**, so the original right button's `kVK_ANSI_F` arrived under the Russian layout as `key:"а"` — Netflix listens for `f`, so it was dead from the day it was written, and nothing reports this (the event is `isTrusted`, on the right target, no error). **(2)** `element.requestFullscreen()` from AppleScript-injected JS is refused — `TypeError: Permissions check failed` — on a **visible, focused** tab with `document.fullscreenEnabled` true and `navigator.userActivation.isActive` true; a hidden tab was the first suspicion and was wrong. From inside a trusted `keydown` the same call succeeded 8/8. **(3)** Netflix's own `f` cannot be that gesture: all eight presses arrived correctly and every one carried `defaultPrevented: true` with zero `fullscreenchange` events — something on the watch page eats it (`ArrowLeft`/`ArrowRight` too; space not), which is why the right button worked for a few presses and then stopped. Hence the listener sits in the **capture** phase on `window` and consumes its keys outright. **(4)** The keys are **F17 and F18**, and which function keys are usable is measured, not chosen: macOS takes some of that range above the browser, and a key it takes never reaches the page *while still firing whatever the system has bound to it*. F16–F20 all arrive; **F14 never does** (the system keeps F14/F15 for screen brightness); and **F13 arrived once and then stopped**, which was reported as both buttons "changing the screen" — a system action firing while Chrome saw nothing. A function key carries no character (no layout can distort it), is absent from this keyboard (it cannot collide with typing), and is **inert in every other app**, which is what makes posting it blind safe where space or `f` would have typed into whatever the user was really working in. Modifier flags are cleared on the event, since a created keyboard event otherwise inherits whatever the user is physically holding. **(5)** Fullscreen means the **window**, via `chrome.windows.update`, not an element on the page. Element fullscreen failed twice over: leaving it never touched the window, so "small screen" left a full-size Chrome behind; and entering it made Netflix resume a paused video off its own `fullscreenchange` (traced three times running, `was: paused → now: playing`). The window API needs no gesture and the page never learns it happened, so neither failure has anywhere to come from — and the player's state is still **held for 1.5s** afterwards as a belt, because a single correction lands before Netflix's; any later press takes ownership of that hold, so it can never fight the user's own next click. **Driving the tab over Apple events was built first and removed**: it worked from the terminal and never from the daemon, because macOS refuses Automation *without prompting* to a process whose bundle carries no `NSAppleEventsUsageDescription`, and adding one means re-signing `GigakuSound.app`, which changes the ad-hoc cdhash and drops the **Accessibility** grant the wheel itself depends on. The extension needs no permission, so that trade disappeared instead of being paid. The tap callback still never does this work itself — `scroll_volume.py` enqueues onto a `maxsize=1` queue drained by a worker thread — because the callback must not block, and because that is where the daemon's log line comes from. That line promises **delivery, not effect**: the daemon cannot see the page. What can is the extension's own trace, written to the DOM (`data-gigaku-remote`, `data-gigaku-remote-log`) because a content script's globals are unreachable from every other world — it answers "is the listener even installed" and "did the button do nothing, or do it and get undone", the two questions that made three straight attempts guesswork. **The extension reloading is itself a failure mode**, and the trace is what named it: the content script Chrome left in an already-open page keeps its listener but loses `chrome.runtime` with the old extension context, so every right-button press answered `Extension context invalidated` while the left one — pure DOM, asking no worker — kept working. Chrome re-injects nothing, so `reinjectRemoteKeys` does, on `onInstalled`/`onStartup` (hence `scripting` + netflix `host_permissions`); and because that lands a second listener beside the orphan, and two live listeners toggle every press twice, each instance claims a **generation** on the shared DOM and the older one stands down. The check runs *before* the event is consumed — an orphan that swallowed the key and then bowed out would be worse than one that never woke up.
- `lib/netflix/__init__.py` imports **nothing**, like `lib/subs/__init__.py`, so the pure-logic modules (and their tests) never pull in pyobjc — `remote` is on the pyobjc side, like `gallery`.
